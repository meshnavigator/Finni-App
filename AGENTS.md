# AGENTS.md — ЛЦТ 2026

Единая каноническая инструкция для coding agents. Переносимые параметры
проекта находятся в `.project-kit/config.json`.

## Контекст

Проект «Питомец Финни» — функциональный прототип Android-приложения для детей
7–11 лет, обучающего планированию, покупкам и накоплениям через игровой цикл с
виртуальным питомцем. Нормативная проектная спецификация —
`docs/ТЗ_Департамент финансов города Москвы.pdf`. Образовательная основа —
`docs/Единая-рамка-ФГ(приложение)-2026.pdf`. Производная спецификация
реализации — `docs/Finni_SRS_v1.3_2026-09-16.md`; DOCX рядом является её
представлением. SRS детализирует реализацию, но не отменяет официальный документ
без Accepted-решения с явным scope.
Целевой стек по ТЗ: React Native + Expo SDK 57 + TypeScript, локальный SQLite,
без сервера. Кодовая база размещается в `Finni App`, но на 2026-09-16 каталог
ещё пуст, поэтому заявленный стек и архитектуру нельзя считать проверенной
реализацией до появления manifest-файлов, кода и успешной сборки.

## Обязательный порядок

1. Прочитай `.project-kit/config.json` и не хардкодь пути, репозиторий и ветки.
2. Для нетривиального изменения проверь `docs/IMPLEMENTATION_DECISIONS.md` и
   `docs/CURRENT_IMPLEMENTATION.md` вместе с релевантным исходным документом.
3. Перед чтением кода используй belief-map workflow из этого файла, если задача
   межмодульная, меняет API/БД/UI-flow или требует blast-radius анализа.
4. Работай в `code_root` из конфигурации.
5. Не редактируй generated, vendor, cache и временные каталоги без прямой
   необходимости задачи.

## Базовые принципы

### Сначала понять

- Не предполагай поведение, которое можно проверить по docs, коду или тестам.
- Формулируй критерий успеха до изменения.
- При нескольких трактовках показывай варианты и последствия.

### Минимальное решение

- Реализуй только запрошенный scope.
- Не добавляй преждевременные абстракции и совместимость, которую не просили.
- Каждая изменённая строка должна иметь прямое отношение к задаче.

### Хирургические изменения

- Не рефактори соседний код без технической необходимости и согласования.
- Не удаляй чужие или unrelated изменения.
- Соблюдай существующий стиль модуля.

### Проверяемый результат

- Баг: воспроизводящий тест или доказуемый сценарий до и после.
- Фича: критерии готовности и тесты контракта.
- UI: runtime/browser проверка.
- Нельзя сообщать «готово» без фактически выполненного Verify.

## Архитектурные правила

Подтверждённых архитектурных инвариантов пока нет. При их появлении для каждого
критического правила укажи:

- каким тестом или проверкой подтверждается правило;
- какие документы и отчёты нужно обновить при изменении.

## Маршрутизация моделей

Политика находится в `.project-kit/model-routing.json`. Для задач разработки
доступны два независимых режима.

### DIRECT — явный выбор одной модели

DIRECT имеет приоритет над автоматической маршрутизацией. Формат:

```text
DIRECT ASTRA HIGH: <задача>
DIRECT SOL XHIGH: <задача>
DIRECT SOL MEDIUM: <задача>
DIRECT LUNA LOW: <задача>
```

Допустимы естественные формулировки `Только Astra: ...` и
`Поручи Sol high: ...`. Если reasoning не указан, используй значение по
умолчанию из policy. `UNO` распознаётся как совместимый псевдоним `LUNA`.

В DIRECT:

- используй `$direct-model-routing`;
- всю содержательную работу выполняет ровно одна выбранная модель;
- не применяй adaptive routing, автоматическую эскалацию, fallback на другую
  модель и межмодельное review;
- если выбранная модель или reasoning недоступны, не подменяй их: сообщи об
  ограничении;
- если текущий поток не совпадает с выбором, он только диспетчеризует задачу
  одному агенту выбранной модели и передаёт его результат пользователю.

### Подтверждение Astra

Перед намеренным выбором или запуском Astra через DIRECT или ADAPTIVE обязательно
получи отдельное подтверждение пользователя. Сам текст `DIRECT ASTRA ...`
является запросом, но не подтверждением: сообщи reasoning, краткую причину и
scope, затем спроси `Разрешаете запустить Astra для этой задачи?` и дождись
явного ответа.

Подтверждение действует только для указанной задачи или пакета. При отказе в
DIRECT остановись без fallback. При отказе в ADAPTIVE продолжай на Sol High,
если пользователь не распорядился иначе. Если пользователь сам открыл основную
задачу на Astra через интерфейс Codex, этот ручной выбор считается
подтверждением для текущей задачи; не спрашивай повторно перед каждым сообщением.

### ADAPTIVE — автоматический выбор

Для нетривиальной задачи разработки без DIRECT и без запрета делегирования
используй `$adaptive-model-routing`. Профили `ADAPTIVE FAST`,
`ADAPTIVE BALANCED` и `ADAPTIVE DEEP` задают приоритет скорости, баланса или
максимальной надёжности. Выбирай исполнителя отдельно для каждого независимого
пакета, а не по фиксированной лестнице моделей.

Активные маршруты: GPT-6 Luna High — механическая работа; GPT-6 Sol Medium —
стандартная реализация; GPT-6 Sol High — архитектура и интеграция; GPT-6 Sol
XHigh — особенно сложная архитектура и `review-all`. GPT-6 Astra High
доступна только при предельном риске после отдельного подтверждения.

### SOLO — текущая модель без делегирования

SOLO не выбирает и не переключает модель. Он сохраняет модель и reasoning уже
открытой задачи Codex и запрещает создавать субагентов или передавать им части
работы. Например, в задаче на Sol команда `SOLO: исправь баг` означает, что
всю работу выполняет текущая Sol. Если нужна конкретная модель, используй
DIRECT вместо SOLO.

При `SOLO`, `без субагентов`, `без делегирования` или `только основной поток`
используй `$solo-execution`. При конфликте DIRECT и SOLO не подменяй намерение:
если выбранная модель не совпадает с текущей, запроси одно уточнение.

## Belief map

Найди codespaces tool root в таком порядке:

1. `belief_map.tool_root` из `.project-kit/config.json`;
2. переменная `CODESPACES_HOME`;
3. `C:\tmp\codespaces-go` или `/tmp/codespaces-go`.

Из `code_root`:

```text
python -B <tool-root>/scripts/build_belief_map.py --full .
python -B <tool-root>/scripts/belief_search.py search "keyword"
python -B <tool-root>/scripts/belief_search.py analyze <full-module-id>
python -B <tool-root>/scripts/belief_search.py deps <full-module-id> 1
python -B <tool-root>/scripts/belief_search.py rdeps <full-module-id> 1
python -B <tool-root>/scripts/belief_search.py boundary <full-module-id> --files
```

Правила:

- сначала `search`/`entity`/`quick`, затем обязательно `analyze`;
- не угадывай module ID;
- читай только файлы из `analyze`/`boundary`, если этого достаточно;
- после изменения imports, routes, SQL, migrations или структуры файлов заново
  выполни полный build;
- `.belief_map.sexp` и cache — generated artifacts, не источник истины;
- исключай `worktrees` и другие копии репозитория из карты.

## Задачи и Git

- Реестр: `tasks/TASKS.md`.
- Task-файл: `tasks/sprint-{N}/S{N}-{NNN}_slug.md`.
- Commit-report: `tasks/commits/sprint-{N}/`.
- Review-report: `tasks/reviews/sprint-{N}/`.
- Итог: `tasks/sprint-{N}/summary/`.
- Рабочая ветка создаётся от `integration_branch`.
- Прямой push в `main_branch` и `integration_branch` запрещён без явного
  разрешения пользователя.
- Внешние GitHub-действия выполнять только если `repository` задан и действие
  входит в запрос пользователя.

## Изменения документации

- Новое или изменённое архитектурное решение фиксируй в
  `docs/IMPLEMENTATION_DECISIONS.md`.
- После значимого изменения фактического поведения обновляй
  `docs/CURRENT_IMPLEMENTATION.md`.
- После изменения workflow обновляй релевантную диаграмму в `docs/mermaid/`.
- Если изменение не влияет на документацию или диаграмму, явно укажи это в
  Verify.

## Проверки

Команды являются конфигурацией проекта и берутся из `.project-kit/config.json`.
Минимум для любого изменения — релевантные тесты и `git diff --check`.
UI-изменения требуют runtime/browser проверки, если она доступна.

## Автономность

Действуй автономно по очевидному безопасному пути. При конфликте источников
истины, архитектурной развилке, рискованном workaround или изменении внешнего
контракта остановись, покажи варианты и запроси решение пользователя.

## После изменения

Ответ должен содержать:

1. что проверено;
2. что изменено и зачем;
3. источники решения;
4. фактический Verify;
5. риски, ограничения и открытые вопросы;
6. влияние на решения, current implementation и диаграммы.
