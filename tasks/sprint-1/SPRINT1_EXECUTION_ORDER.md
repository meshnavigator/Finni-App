## Critical path

`P0 baseline -> S1-001 -> S1-002 -> S1-003 -> S1-004 -> S1-006 -> S1-005

S0-006 идёт отдельным carry-over потоком и должен быть закрыт до итогового PASS
Sprint 1. По записанным зависимостям ни одна задача Sprint 1 не образует
полностью независимую параллельную ветвь реализации.

## Возможные параллельные потоки

- Параллельно с S1-001 можно готовить только тестовые таблицы, fixtures и
  traceability, не фиксируя конкурирующий доменный контракт.
- После стабилизации contracts S1-001 можно заранее готовить UI-сценарии и
  ассеты S1-004, но интеграция onboarding/home ждёт S1-002 и S1-003.
- S0-006 можно выполнять параллельно с ранними доменными задачами в отдельном
  потоке, поскольку он проверяет сохранённый Sprint 0 APK, а не незавершённый
  код Sprint 1.
- Runtime/device проверки нельзя проводить по сборке, изменяемой другим
  исполнителем; версия APK и её SHA-256 должны быть явно зафиксированы.

Один worktree допускает только одного пишущего исполнителя; параллельность
возможна лишь при разделённых worktrees и несоприкасающихся файлах.

## Нельзя запускать как независимую работу

- Любую task-ветку до фиксации bootstrap baseline и подтверждения точки
  ветвления согласно `.project-kit/config.json`.
- S1-002 до S1-001: схема, ограничения и idempotency зависят от доменных типов
  и command contracts.
- S1-003 до S1-002: lifecycle должен опираться на атомарные команды, receipts и
  разделённые normal/demo базы.
- S1-004 до S1-002 и S1-003: UI не должен имитировать несохранённый профиль,
  баланс, период или режим.
- S1-005 до S1-004: plan/fact входит в пользовательскую вертикаль и требует
  работающего профиля, shell и восстановления состояния.
- Подменять SQLite in-memory mock-ом в restart/migration evidence или считать
  component test доказательством фактического сохранения после перезапуска.
- Закрывать денежные и lifecycle gates только happy-path тестами без numeric
  boundaries, ROLLBACK, idempotency, time anomalies и mode isolation.

## Общий Definition of Done

- Выполнены критерии приёмки и Verify из каждого task-файла; без completion
  evidence задача не помечается завершённой.
- Профиль, выбранный питомец, денежное состояние и план восстанавливаются после
  закрытия и повторного запуска приложения.
- Деньги хранятся целыми безопасными значениями; отрицательные балансы, дроби,
  unsafe integers и повторное начисление отклоняются доказуемыми тестами.
- Денежные команды атомарны и идемпотентны; журнал, проекции, события и receipts
  согласованы после COMMIT, ROLLBACK и повторного открытия SQLite.
- Normal/demo режимы изолированы, а пять demo-периодов выполняются без ожидания
  и без влияния на normal данные.
- Выполнены зарегистрированные `npm run lint`, `npm run typecheck`,
  `npm run test`, `npm run content`, `npm run fixtures`, релевантные runtime и
  persistence проверки, а также `git diff --check` внутри `Finni App`.
- После imports, SQL, migrations, routes или структурных изменений выполнен
  полный rebuild belief map и проверены затронутые module boundaries.
- При изменении архитектуры, workflow или фактического поведения обновлены
  `IMPLEMENTATION_DECISIONS.md`, `CURRENT_IMPLEMENTATION.md` и релевантная
  Mermaid-диаграмма — либо в Verify явно зафиксировано отсутствие влияния.
