# S4-005: Подготовить документацию, трассируемость и черновик карточки

## Цель
Собрать комплект, по которому сторонний специалист собирает APK, воспроизводит demo и понимает соответствие требованиям.

## Контекст
Документация относится к одной версии кода и не может отмечать функции реализованными без доказательства.

## Состав работ
- создать README, environment/build/demo/reset инструкции;
- описать архитектуру, данные, экономику, контент и доступность;
- заполнить FR/NFR/A.1–A.12 traceability ссылками на код/tests;
- подготовить тест-отчёт, ограничения, licenses и release scope;
- подготовить название, описания, иконку 512 и минимум 3 скриншота без публикации.

## Источники
- официальное ТЗ, §§3.3, 5, 7.1;
- SRS v1.3, §§22.1–22.8, 24;
- DEV-16/17/27/31; NFR-16/19.

## Критерии приёмки
- clean build воспроизводим по README;
- каждая заявленная функция имеет доказательство той же версии;
- минимум 3 ключевых экрана и честная status matrix готовы;
- карточка подготовлена, но не опубликована.

## Зависимости
- S4-001, S4-003, S4-004, S3-007.

## Verify
- пройти README на чистом окружении;
- автоматическая проверка ссылок/ID/manifest;
- визуальная проверка иконки/скриншотов;
- сверка версии APK, commit и docs.

## Out of scope
- презентация и питч;
- публикация в RuStore.

На Windows `core.autocrlf=true` меняет байты 13 tracked bundle JSON при
checkout, поэтому текущий raw-byte content validator видит неверные SHA-256
при чистом Git status. В `.gitattributes` добавлено `content/bundles/** -text`:
проверка `git checkout-index --temp` для `catalogs/assets.json` получила SHA
из manifest. Полный Verify на свежем checkout с этим правилом ещё не выполнен;
существующие checkout требуют отдельного обновления файлов. Задача остаётся
открытой.
